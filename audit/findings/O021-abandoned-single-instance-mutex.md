- [x] **W_O021 — O021 abandoned single-instance mutex finding — WITHDRAWN as false positive**
  - **State:** Withdrawn after characterization; no production change is required for the originally claimed next-launch crash.
  - **Original claim:** A prior youtube-dl-gui process that terminates while owning the named single-instance mutex could leave that mutex abandoned so the next application launch would receive `AbandonedMutexException` from `WaitOne` and escape `Main`.
  - **Correction:** The claim omitted named-kernel-object lifetime. An abandoned mutex remains observable only while at least one handle to that same mutex object survives the owner thread's termination. When the application process is the sole handle owner, process termination closes its final handle and the named mutex object is destroyed. A later application process creates a fresh mutex object; it does not inherit the abandoned state of the destroyed object. The ordinary single-instance path does not establish a surviving third-party handle across application termination.
  - **Characterization evidence:** The first synthetic test deliberately kept a handle alive in the audit process after its owner thread exited. That can create an abandoned mutex, but it does not model the claimed previous-process-crash/next-process-launch sequence. The guarded repair request at `a7e81fcf7e37c5cdecefc7b0f7d66c1d61e437ed` therefore failed its regression and published no source change. The corrected regression now abandons a named mutex, closes its final surviving handle, and verifies that a subsequent opener acquires a fresh mutex without `AbandonedMutexException`.
  - **Residual note:** If some unrelated process intentionally keeps a handle to this named mutex open while the application owner terminates, abandonment can be observed on that surviving kernel object. That is not the normal single-instance lifecycle described by O021 and is not sufficient evidence for changing startup behavior.
  - **Disposition:** Preserve the current production behavior. Do not add an abandoned-mutex recovery path merely to satisfy the withdrawn synthetic test. The separate question of recursive ownership from `new Mutex(true, ...)` followed by `WaitOne` is not promoted here because `Main` returns immediately after its final release path and process teardown closes the handle; any distinct observable defect requires its own evidence.
