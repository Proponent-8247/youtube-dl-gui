- [ ] **O037 — FFmpeg ZIP extraction has no uncompressed-size bound**
  - **Priority / state:** Medium / storage exhaustion and update robustness; SOURCE-CONFIRMED.
  - **Finding:** `Updater.UpdateFfmpeg` opens the downloaded FFmpeg ZIP, locates entries named `ffmpeg.exe` and `ffprobe.exe`, and extracts each directly to `.update` files with `ExtractToFile`. It does not validate `ZipArchiveEntry.Length`, compressed-to-uncompressed ratio, an expected executable size, or a cumulative extraction budget before writing. A compact archive with extremely large selected entries can therefore consume arbitrary disk space during extraction. This remains a separate boundary from O027: bounding the downloaded archive bytes alone does not bound ZIP expansion.
  - **Evidence:** `youtube-dl-gui/Updater/Updater.cs`, `UpdateFfmpeg`: after selecting `FfmpegEntry` and `FfprobeEntry`, the code deletes stale temp paths and executes `await Task.Run(() => FfmpegEntry.ExtractToFile(FfmpegTempPath))` followed by the equivalent ffprobe extraction. No entry-length or expansion check precedes either extraction. The archive is third-party update input and O019 separately tracks lack of cryptographic artifact verification.
  - **Audit rationale checkpoint:** The replacement transaction protects the previous binaries, but it does not protect storage availability. A safe patch should impose provider-appropriate uncompressed limits before and while copying each selected entry; metadata such as `ZipArchiveEntry.Length` is useful for early rejection but should not be the sole runtime enforcement. Do not apply a tiny universal limit that breaks legitimate future FFmpeg builds.
  - **Acceptance for patch pass:** Build controlled ZIP fixtures containing normal ffmpeg/ffprobe entries, oversized declared entries, high compression-ratio entries, truncated streams, duplicate executable names, and one normal plus one oversized executable. Assert rejection occurs before or at the configured extraction budget, partial `.update` files are removed, the prior executable pair remains intact, cancellation remains responsive, and legitimate current/future-sized fixtures succeed. Test the bound independently of the O027 network-download byte limit.
