# End-to-end review checklist — continuation 3

This file continues `audit/FINDINGS-CHECKLIST.md`, `audit/END-TO-END-REVIEW-CHECKLIST.md`, and `audit/END-TO-END-REVIEW-CHECKLIST-2.md`. Findings are committed individually for interruption-safe recovery. Production source is unchanged in this review pass.

- [ ] **O023 — Successful FFmpeg replacement can be reported as an unhandled failure when archive cleanup fails**
  - **Priority / state:** Medium / update fault handling and post-commit cleanup; SOURCE-CONFIRMED.
  - **Finding:** `Updater.UpdateFfmpeg` performs the download, extraction, pair replacement, and rollback-capable work inside its retry/error boundary. After that boundary completes successfully, it calls `File.Delete(FfmpegZipPath)` outside any `try/catch`. If the downloaded ZIP is locked, ACL-restricted, read-only in a way that prevents deletion, or otherwise undeletable at that moment, the method throws **after** the new ffmpeg/ffprobe pair has already been installed. The Settings caller is an `async void` event handler with no surrounding catch, so this post-success cleanup exception can become an unhandled UI-thread exception; first-run setup can also be failed even though the tools were installed. The remaining ZIP is cleanup residue, not a reason to roll back a verified successful replacement.
  - **Evidence:** `youtube-dl-gui/Updater/Updater.cs`, `UpdateFfmpeg`: extraction/replacement is guarded through the `do/try/catch` ending around line 428; line 431 unconditionally calls `File.Delete(FfmpegZipPath)` afterward, then refreshes verification and returns true. The temp-file cleanup inside the guarded operation already treats cleanup failures as diagnostics, demonstrating a different and safer policy for non-critical residue.
  - **Audit rationale checkpoint:** Installation success and cleanup success are different state transitions. Once both executables have been committed successfully, failure to remove the downloaded archive should be contained/logged and should not make callers believe the install itself failed or let an exception escape an `async void` UI handler. This is distinct from O008 deterministic temp-name collisions and O022 form-lifetime continuation.
  - **Acceptance for patch pass:** Complete a controlled FFmpeg update while another fixture holds the ZIP so deletion fails. Assert the installed ffmpeg/ffprobe remain the new pair, the method returns/report state consistently with successful installation (with a cleanup warning if desired), verification refreshes, and no unhandled exception reaches Settings or first-run setup. Also test download/extraction/replacement failures still return failure and preserve/restore old binaries; retry/cleanup behavior must not accidentally delete a user file unrelated to the update.

- [ ] **O024 — Batch-from-file worker can outlive/disconnect from the main form and lets startup/file errors escape the worker thread**
  - **Priority / state:** Medium / batch lifecycle and application shutdown; SOURCE-CONFIRMED.
  - **Finding:** `frmMain.mBatchDownloadFromFile_Click` starts a raw foreground `Thread` that is not registered as a processing action before it begins work. Its first operation marshals state through `this.Invoke` with no `IsDisposed`/handle guard or exception boundary; it then calls `File.ReadAllLines` on the selected text file with no catch. If the main form closes before the worker reaches/completes that `Invoke`, or if the selected file becomes inaccessible after the file dialog (delete/ACL/lock/I/O failure), an exception escapes the raw worker thread. The main form can finish its own close path while `RunningActions` is still empty because the first child downloader has not yet been shown, leaving this foreground worker disconnected from the application's normal action/exit ownership. This path is separate from `frmBatchDownloader`, whose worker was explicitly corrected to use an STA and processing-form lifecycle.
  - **Evidence:** `youtube-dl-gui/Forms/frmMain.cs`, `mBatchDownloadFromFile_Click`: creates `Thread BatchThread`, calls `this.Invoke(...)` around lines 941-964, later calls `File.ReadAllLines(TextFile)`, creates modal `frmDownloader` instances, and finally starts the raw thread with no outer `try/catch`, cancellation token, processing-form registration, or pre-Invoke disposal check. `Program.Main` decides whether to enter `AwaitActions()` based on `RunningActions` after `frmMain.ShowDialog()` returns; the raw thread itself is not represented there.
  - **Audit rationale checkpoint:** Batch-from-file is intended functionality, so the fix should preserve sequential modal downloads and existing abort semantics rather than replacing the feature wholesale. The worker needs explicit ownership from launch through first child creation, contained input-file errors, and shutdown behavior that cannot invoke a disposed main form or keep the process alive invisibly.
  - **Acceptance for patch pass:** Use a controlled batch file and introduce delays before state capture, before file read, and before first downloader creation. Close the main form at each point; delete/lock/deny the batch file after selection; and inject a malformed/unreadable line source. Assert no unhandled worker exception, invisible foreground-thread hang, or invocation of disposed controls. If shutdown should wait, expose/track the operation as active work; if it should cancel, stop before launching further downloads. Preserve normal sequential batch behavior, per-item abort, selected quality/format/custom arguments, and file-read diagnostics.

- [ ] **O025 — `args.txt` custom-argument persistence lets ordinary file I/O failures escape initialization, tray actions, and form closure**
  - **Priority / state:** Medium / persistence fault containment; SOURCE-CONFIRMED.
  - **Finding:** When `General.SaveCustomArgs == 1`, the application treats `args.txt` in the program directory as persistent custom-argument storage but performs its reads/writes without a containing I/O boundary. `CustomArguments` static initialization calls `File.ReadAllLines` after only `File.Exists`; access can fail and surface as a type-initializer failure when the custom-argument subsystem is first touched. The tray custom-download action separately calls `ReadAllText` and then `ReadAllLines` with no catch, so deletion/ACL/lock/I/O changes between those calls can escape an ordinary UI event. `frmMain_FormClosing` calls `File.WriteAllLines` with no catch; a write failure can abort/throw out of the close sequence after other state has begun to mutate. This is not the same as historical INI-write handling: `args.txt` is a separate persistence mode with independent uncontained filesystem calls.
  - **Evidence:** `youtube-dl-gui/Config/Interfacing/CustomArguments.cs` static constructor selects `File.ReadAllLines(Environment.CurrentDirectory + "\\args.txt")` when mode 1 and the file exists. `youtube-dl-gui/Forms/frmMain.cs`, `cmTrayDownloadCustomTxt_Click`, checks existence then performs unguarded `ReadAllText` and `ReadAllLines`; `frmMain_FormClosing` unconditionally calls `File.WriteAllLines` for mode 1. None of these paths has an I/O catch/recovery policy.
  - **Audit rationale checkpoint:** Custom arguments are user preferences; an inaccessible optional persistence file should not destabilize startup, tray actions, or shutdown. The fix should not silently discard a user's stored argument list or change the selectable persistence modes. Read failures need a contained fallback/diagnostic, and write failures need a user-visible or logged failure policy that keeps the close sequence internally consistent.
  - **Acceptance for patch pass:** Exercise missing, empty, locked, access-denied, read-only, deleted-between-check-and-read, directory-in-place-of-file, and disk/write-failure fixtures. Trigger initial custom-argument loading, tray custom download, and main-form close. No unhandled exception/type-initializer failure may escape; existing in-memory custom arguments and selected index must remain usable. A failed write must not falsely report persistence success or corrupt an existing `args.txt`; a successful normal read/write must preserve ordering, duplicates policy, Unicode, quotes, and repeated spaces.

- [ ] **O026 — Merger accepts stream metadata without `format.filename` and later null-dereferences it when generating the merge**
  - **Priority / state:** Low-to-Medium / external metadata robustness; SOURCE-CONFIRMED.
  - **Finding:** `frmMerger.AddFileAsync` accepts a deserialized ffprobe result whenever `MediaStreams` exists and contains at least one stream. It does not require `FfprobeData.Format` or `Format.filename`. The UI then allows the accepted streams to be selected. `GenerateList` later dereferences `CurrentFile.ParentFile.Format!.filename!` to deduplicate inputs and build `-i` arguments. A controlled/custom ffprobe executable, malformed-but-deserializable ffprobe output, or unexpected probe schema that contains streams but omits the format object/filename can therefore pass the load boundary and produce a `NullReferenceException` on the Merge button instead of being rejected/contained when the probe result is imported.
  - **Evidence:** `youtube-dl-gui/Forms/frmMerger.cs`, `AddFileAsync`: the acceptance predicate checks only form lifetime, `NewData`, and `NewData.MediaStreams.Length`; the loaded object is added to `LoadedMediaFiles`. `GenerateList` then uses `ParentFile.Format!.filename!` without a null check. `FfprobeData.Format` and `FfprobeSubdata.Format.filename` are explicitly nullable because JSON deserialization may omit them.
  - **Audit rationale checkpoint:** The merger already has the authoritative user-selected `FilePath`, so missing probe-format filename should not need to crash or discard otherwise valid stream metadata. A narrow correction can validate/fallback at ingestion or use the tracked input path consistently without weakening stream detection. Do not assume the null-forgiving operator makes externally deserialized fields non-null.
  - **Acceptance for patch pass:** Feed controlled ffprobe JSON with streams plus normal format/filename, missing `format`, `format: null`, missing/blank `filename`, and a filename that differs from the selected input path. Select streams and generate/launch merge arguments. No UI exception may escape; each `-i` must refer to the intended selected file exactly once, output-overwrite protection must compare against the same canonical input paths, and normal ffprobe output must remain unchanged. Add an end-to-end merger regression using a controlled ffprobe fixture rather than only constructing `FfprobeData` directly.
