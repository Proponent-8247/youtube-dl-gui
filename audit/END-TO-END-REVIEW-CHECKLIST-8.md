# End-to-end review checklist — continuation 8

This file continues the prior end-to-end audit checklists. Findings are committed individually for interruption-safe recovery. Production/application source is unchanged in this review pass.

- [ ] **O043 — `ExtendedLinkLabel` hover handling destroys caller-configured link colors**
  - **Priority / state:** Low / shared-control behavior; SOURCE-CONFIRMED deterministic property-contract defect.
  - **Finding:** `ExtendedLinkLabel` publicly re-exposes `ActiveLinkColor`, `LinkColor`, and `VisitedLinkColor`, so callers/designer code can configure the normal link colors. However `OnMouseEnter` unconditionally replaces `LinkColor` and `VisitedLinkColor` with the class's hard-coded hover colors, and `OnMouseLeave` unconditionally replaces them again with the class's hard-coded default colors. The control never preserves the values a caller assigned before hover. Consequently any non-default normal/visited color survives only until the first mouse enter/leave cycle, after which the caller's configured state is silently lost. This is a control-contract defect even though the reviewed shipping forms currently appear to rely on the defaults; it is not a request to mass-theme the application.
  - **Evidence:** `Controls/ExtendedLinkLabel.cs`: the new public color properties directly proxy the base properties; the constructor initializes hard-coded defaults; `OnMouseEnter` assigns `DefaultHoverColor`/`VisitedHoverColor`; `OnMouseLeave` assigns `DefaultColor`/`VisitedColor` rather than restoring the prior configured values. No existing O/F checklist item covers this reusable-control state loss.
  - **Audit rationale checkpoint:** Preserve the current default and hover appearance for callers that never customize colors. If customization is supported by the exposed properties, keep caller-selected normal/visited colors as durable state and derive/store hover colors separately; alternatively make the customization contract explicit rather than silently accepting values that are later discarded. Do not introduce application-wide appearance refactoring while fixing this control.
  - **Acceptance for patch pass:** Instantiate the real control with defaults and with custom normal/visited colors, trigger repeated mouse enter/leave cycles, disabled/enabled transitions and handle recreation, and verify caller-configured values remain stable after hover while default callers retain the current appearance. Exercise designer/property assignment both before and after handle creation and confirm no event-order regression in normal link activation.

- [ ] **O044 — Second-resolution batch folder IDs can merge independent batch runs into one output directory**
  - **Priority / state:** Low-to-Medium / batch output isolation; SOURCE-CONFIRMED concurrency/collision defect.
  - **Finding:** `BatchHelper.CurrentTime` identifies a batch only as `yyyy_MM_dd-HH_mm_ss`. `frmBatchDownloader` captures that value once when a batch starts and assigns it to every `DownloadInfo.BatchTime`; when separate batch downloads and date folders are enabled, `DownloadInfo.GenerateArguments` uses the value directly under `# Batch Downloads #`. The main form allows an unrestricted new `frmBatchDownloader` each time the Batch Download menu action is invoked. Two independent batch windows started during the same wall-clock second therefore receive exactly the same batch identifier and write into the same nominally separated batch folder. This can intermingle output from independent queues and also increases filename/archive collision risk when their schemas overlap. It does not require clock rollback; ordinary concurrent launches inside one second are sufficient.
  - **Evidence:** `youtube-dl-gui/Classes/BatchHelper.cs` returns `$"{DateTime.Now:yyyy_MM_dd-HH_mm_ss}"`. `youtube-dl-gui/Forms/frmMain.cs`, `mBatchDownload_Click`, always creates and shows a new `frmBatchDownloader` without single-instance gating. `frmBatchDownloader.btnBatchDownloadStartStopExit_Click` captures `string BatchTime = BatchHelper.CurrentTime` and supplies it to each `DownloadInfo`. `youtube-dl-gui/Classes/DataClasses/DownloadInfo.cs` appends `BatchTime` beneath `# Batch Downloads #` when `SeparateBatchDownloads` and `AddDateToBatchDownloadFolders` are enabled.
  - **Audit rationale checkpoint:** Preserve human-readable batch grouping and current settings semantics, but give each independently started batch an identifier that is unique enough for concurrent operation. Do not solve this by globally serializing downloads or disabling multiple batch windows unless product behavior explicitly chooses that tradeoff. A suffix/unique directory allocation can retain the readable timestamp while preventing accidental folder sharing.
  - **Acceptance for patch pass:** Start two or more real Batch Downloader windows in the same second with separate-batch/date-folder settings enabled and overlapping output schemas. Every independently started batch must resolve to a distinct output directory while all items inside one batch share its directory. Repeat with rapid sequential starts, clock adjustments, pre-existing timestamp-named folders, Unicode/download-root variants, and settings with date folders disabled. Existing intentional behavior when batch separation is disabled must remain unchanged.
