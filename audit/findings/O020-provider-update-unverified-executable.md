- [ ] **O020 — Downloader-provider updates are installed without cryptographic verification**
  - **Priority / state:** High / executable supply-chain integrity; SOURCE-CONFIRMED.
  - **Finding:** The non-internal `Updater.UpdateYoutubeDl` path constructs a GitHub release-asset URL for the selected yt-dlp/youtube-dl provider and downloads that `.exe` directly into the configured provider path through `frmGenericDownloadProgress`. Success is followed by location refresh and the release is marked no longer newer, but no expected SHA-256, signature, signed checksum manifest, or publisher verification is applied to the downloaded executable before it becomes the binary the application later launches. This is separate from the provider's own `-U` path and from O019's FFmpeg archive.
  - **Evidence:** `youtube-dl-gui/Updater/GithubLinks.cs` defines direct release-asset URLs for `yt-dlp/yt-dlp`, `yt-dlp/yt-dlp-nightly-builds`, `ytdl-org/youtube-dl`, and `ytdl-patched/youtube-dl`. `Updater.UpdateYoutubeDl(false, ...)` constructs that URL, runs `frmGenericDownloadProgress` with the live provider destination, and on `DialogResult.OK` immediately refreshes provider location and accepts the update. `GithubData.ExecutableHash` is populated from release-body text for the application updater model but is not checked by this provider-install path.
  - **Audit rationale checkpoint:** HTTPS plus a GitHub repository identity is not the same as application-level artifact verification. These files are executable dependencies and are invoked with user-supplied media arguments and credentials. A correction must use verification metadata actually published by each supported provider; do not assume all four repos expose the same checksum format or invent hashes for moving release URLs.
  - **Acceptance for patch pass:** For each supported provider/update channel, define the authoritative checksum/signature source and validate the exact downloaded executable before replacement. Test matching executable, modified bytes, missing/malformed verification metadata, wrong-provider metadata, nightly/stable switching, cancellation, retry, and preservation of the previously working binary on verification failure. If a provider has no acceptable authenticity mechanism, require an explicit product-policy decision rather than silently treating transport success as verification.
