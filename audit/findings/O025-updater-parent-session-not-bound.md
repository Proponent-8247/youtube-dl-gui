- [ ] **O025 — Updater does not bind the supplied parent window, process ID, and replacement target into one trusted session**
  - **Priority / state:** Medium / local IPC and replacement trust boundary; SOURCE-CONFIRMED.
  - **Finding:** `youtube-dl-gui-updater` accepts `-hwnd` and `-pid` independently from its command line. When both are nonzero it stores them as `ApplicationHandles`, opens the supplied PID with `Process.GetProcessById`, and later accepts `WM_COPYDATA` whenever `m.WParam` equals the supplied HWND. It never verifies that the HWND belongs to that PID, that the process is the expected youtube-dl-gui parent, or that the message belongs to the launch session. The accepted `UpdateData` supplies `FileName`, version, and expected hash; `RunUpdate` later waits for the arbitrary PID, downloads the upstream application, replaces the supplied same-user-writable `.exe` path, and launches it. A local same-user process can therefore launch the updater with its own window plus an unrelated/live PID and drive the updater's replacement workflow outside the intended parent-child session. This finding does not claim privilege escalation: file replacement remains limited by the updater process's existing permissions.
  - **Evidence:** `youtube-dl-gui-updater/Program.cs` parses `-hwnd` and `-pid` independently and constructs `new ApplicationHandles(Handle, ProcessID)` with no relationship check. `Forms/frmUpdater.cs` calls `Process.GetProcessById(ApplicationData.ProcessID)`, accepts `WM_COPYDATA` based only on `m.WParam == ApplicationData.MessageHandle`, assigns the received `UpdateData.FileName`, and later moves/replaces that filename and `Process.Start`s it. The main application's opposite direction is separately tracked by O007.
  - **Audit rationale checkpoint:** A window handle is not an authentication token, and a PID supplied on the command line does not prove the sender window and process are the launched parent. At minimum the updater should verify HWND ownership with the native process ID and expected executable/session identity; a per-launch nonce or inherited authenticated channel would provide stronger binding. The fix must preserve the synchronous acknowledgement protocol and must not kill or overwrite an unrelated process/file on validation failure.
  - **Acceptance for patch pass:** Launch the updater with (1) valid parent HWND/PID, (2) attacker-owned HWND plus valid app PID, (3) valid HWND plus unrelated PID, (4) stale/reused HWND, (5) exited PID, and (6) forged `UpdateData.FileName`. Only the valid session may receive/send update data or replace/launch the application. Verify sender-window PID ownership, expected parent executable identity, replacement target confinement to the parent executable path, and rejection before any file/network side effect. Add race coverage for PID/HWND reuse and preserve normal update acknowledgement.
