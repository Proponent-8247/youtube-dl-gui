# End-to-end review checklist — continuation 2

This file continues `audit/FINDINGS-CHECKLIST.md` and `audit/END-TO-END-REVIEW-CHECKLIST.md`. Each newly confirmed issue is committed before review proceeds so interruption leaves a recoverable audit trail. Entries contain concise audit rationale, source evidence, and patch-pass acceptance criteria; they do not contain private chain-of-thought. Production code is not changed in this pass.

- [ ] **O016 — Authenticated download secrets are exposed in child-process command lines**
  - **Priority / state:** Medium / local credential confidentiality; SOURCE-CONFIRMED.
  - **Finding:** Authentication passwords, two-factor values, and media passwords are decrypted and appended directly to the downloader process command line as `--password`, `--twofactor`, and `--video-password`. The application correctly masks these values in its own preview/log strings, but the actual `ProcessStartInfo.Arguments` still contains the plaintext secrets. On Windows, process command lines can be inspected by sufficiently capable local processes (including same-user/debug-capable tooling), and crash/diagnostic tooling can capture them. DPAPI protection of the stored byte arrays therefore does not protect the secret while the downloader child is running.
  - **Evidence:** `youtube-dl-gui/Classes/DataClasses/DownloadInfo.cs`, `youtube-dl-gui/Classes/DataClasses/ExtendedMediaDetails.cs`, and `youtube-dl-gui/Classes/DataClasses/YoutubeDlData.cs` call `Authentication.GetPassword()` / `GetMediaPassword()` and concatenate the returned plaintext into downloader CLI arguments. The older `youtube-dl-gui/Classes/DownloadInfo.cs` has the same pattern but is excluded by the current project file and is evidence of legacy duplication, not shipping reachability. Download forms launch the generated included-code strings through `ProcessStartInfo.Arguments`.
  - **Audit rationale checkpoint:** The existing censored preview only protects application logs/UI; it does not change the operating-system-visible command line. The patch pass should use a downloader-supported secret transport that does not place plaintext credentials in argv (for example, a tightly permissioned ephemeral configuration/input mechanism if compatible with all supported providers) and must preserve current authentication functionality. Do not silently remove password-based authentication merely to close this finding.
  - **Acceptance for patch pass:** Run authenticated quick, extended, metadata-probe, batch, and retry flows with controlled credentials containing spaces, quotes, Unicode, and empty optional fields. Inspect the spawned child command line and application logs and assert no password/2FA/media-password plaintext appears. Verify the downloader still receives the exact secret through the replacement mechanism; ephemeral secret material is access-restricted, deleted on success/failure/cancellation, and never reused across unrelated jobs. Document any provider mode for which a non-argv secret channel is impossible rather than weakening authentication silently.

- [ ] **O017 — Diagnostic logging records complete source URLs, including potentially sensitive query/userinfo data**
  - **Priority / state:** Medium / diagnostic-data confidentiality; SOURCE-CONFIRMED.
  - **Finding:** Several normal code paths log the full user/media source string without redaction. `YoutubeDlData` logs complete URLs while gathering metadata, the quick downloader logs `CurrentDownload.DownloadURL`, `Program.ProcessCopyData` logs the URL received over IPC, and extended-downloader error paths include the media URL. For signed URLs, bearer-like query parameters, embedded URI credentials, private share tokens, or other secret-bearing links, those values are retained in the application's diagnostic log/debug output. This is distinct from O016: even if CLI credentials are moved out of argv, a token carried inside the URL can still be disclosed by normal application diagnostics.
  - **Evidence:** `youtube-dl-gui/Classes/DataClasses/YoutubeDlData.cs` logs `URL` before/after metadata retrieval and thumbnail work; `youtube-dl-gui/Forms/frmDownloader.cs` logs `CurrentDownload.DownloadURL`; `youtube-dl-gui/Program.cs` logs `ProcessCopyData called: {Type} > {URL}`; `youtube-dl-gui/Forms/frmExtendedDownloader.cs` includes `Media.URL` in thumbnail/queue failure logging. `Log.Write` forwards the text to the log form and `Debug.Print` unchanged.
  - **Audit rationale checkpoint:** Downloader operands intentionally include arbitrary site URLs and some provider-specific expressions, so logging cannot assume query strings are harmless. Diagnostics should retain enough origin/context to troubleshoot without persisting secrets by default. Raw provider stdout/stderr is a separate diagnostic surface and should be reviewed explicitly rather than claiming one sanitizer covers all third-party output.
  - **Acceptance for patch pass:** Exercise ordinary HTTP(S) URLs, URI userinfo, signed query strings, fragments, local paths, search expressions, and provider-specific pseudo-URLs. Normal logs and copied diagnostic text must not contain secret query values/userinfo while still identifying the host/path or a stable redacted representation. Verify error dialogs and exception extra-info do not reintroduce the raw link. Decide and document how opt-in verbose/raw provider output is handled, rather than silently stripping content users explicitly requested for debugging.

- [ ] **O018 — Metadata duration formatting has input-proportional subtraction loops that can stall the UI**
  - **Priority / state:** Medium / availability and metadata robustness; SOURCE-CONFIRMED.
  - **Finding:** `YoutubeDlData.Duration` converts provider-reported seconds into minutes/hours by repeatedly subtracting 60 in `while` loops. `DurationTime` is a deserialized `decimal?`, and playlist duration sums every entry before the same conversion. A very large but parseable duration therefore causes work proportional to the duration value (for example, one billion seconds requires roughly 16.7 million minute-subtraction iterations) instead of constant-time arithmetic. The formatted value is read while binding extended-downloader metadata to UI controls, so malformed/extreme provider output can make the UI appear hung even though no network or child-process work is pending.
  - **Evidence:** `youtube-dl-gui/Classes/DataClasses/YoutubeDlData.cs`, `Duration` getter: `while (seconds >= 60) { minutes++; seconds -= 60; }` followed by `while (minutes >= 60) { hours++; minutes -= 60; }`. `DurationTime` is populated from downloader JSON; `frmExtendedDownloader` reads `MediaDetails.MediaData.Duration` for the timestamp label and queue row.
  - **Audit rationale checkpoint:** This is an algorithmic correctness issue, not a request to cap legitimate long media. The same visible formatting can be produced with division/remainder in bounded time. Playlist aggregation should also handle overflow/extreme values deterministically rather than using duration magnitude as CPU work.
  - **Acceptance for patch pass:** Test fractional seconds and ordinary durations around 59/60/3599/3600 seconds, 24+ hour media, very long playlists, very large decimal durations, negative/invalid values from controlled metadata, and aggregation overflow boundaries. Formatting must complete within a fixed small deadline independent of duration magnitude, preserve the existing normal display format, and never block the UI thread with value-proportional loops.

- [ ] **O019 — Approximate media-size calculation can overflow on extreme provider metadata and abort format parsing**
  - **Priority / state:** Low-to-Medium / metadata robustness; SOURCE-CONFIRMED.
  - **Finding:** When yt-dlp omits `filesize`/`filesize_approx`, the extended downloader estimates size from deserialized `decimal` duration and bitrate values. `GetApproximateVideoSize` and `GetApproximateAudioSize` multiply those values without range checks, then call the shared decimal `SizeToString`, which rounds and casts the result to `long`. Values can therefore overflow either the decimal multiplication or the decimal-to-Int64 cast. The calls happen while `ExtendedMediaDetails.Parse` builds format rows, so one extreme format can throw and make metadata retrieval for the entire item fail instead of displaying an unknown/unavailable estimate.
  - **Evidence:** `youtube-dl-gui/Classes/DataClasses/YoutubeDlData.cs`: estimated size is calculated as `DurationTime.Value * bitrate * 1024`; `Controls/Extensions.cs` decimal `SizeToString` performs `return ((long)size).SizeToString(...)` with no bounds check. `ExtendedMediaDetails.Parse` calls these helpers for format rows whenever provider-reported size is null.
  - **Audit rationale checkpoint:** Size is presentation metadata, not a reason to reject an otherwise valid downloadable format. A safe implementation should handle nonsensical/overflowing provider estimates by showing an unknown or bounded representation while preserving normal estimates. This is distinct from O018: O018 is value-proportional duration formatting/aggregation; O019 is unchecked arithmetic/conversion in optional size estimation.
  - **Acceptance for patch pass:** Feed controlled format metadata at normal bitrates/durations, zero/negative values, values near `long.MaxValue`, decimal multiplication limits, and multiple formats where only one estimate is extreme. Metadata parsing must complete, ordinary estimates must remain unchanged, and an unrepresentable estimate must not discard the media item or other formats. Add a regression that exercises the compiled `ExtendedMediaDetails` parse/format-row path rather than only testing the extension method.

- [ ] **O020 — Malformed boolean INI values silently become false instead of using the setting default**
  - **Priority / state:** Low / configuration resilience and compatibility; SOURCE-CONFIRMED.
  - **Finding:** `IniProvider.Read(bool Value, bool Default, ...)` returns `true` only for `true`, `on`, or `1`; every other existing nonblank value returns `false`. The supplied `Default` is used only when the key is missing. Consequently a malformed/stale value such as `maybe`, a typo, or an unsupported legacy token silently disables settings whose defined default is `true` (for example several download/UI defaults), rather than falling back to that setting's default. This differs from the integer/Version readers, which use `TryParse` and return the caller's default on invalid data.
  - **Evidence:** `youtube-dl-gui/Config/Interfacing/IniProvider.cs`, boolean `Read`: after `InternalKeyExists`, the switch maps recognized truthy strings to true and `_ => false`; it never distinguishes recognized false values from invalid values or returns `Default` for an invalid token. Static configuration classes pass both true and false defaults through this helper.
  - **Audit rationale checkpoint:** This is not a request to reject hand-edited INI files or change valid false syntax. The parser should define accepted true/false tokens and use the documented/default value when an existing token is not recognized, matching the resilience pattern of the numeric readers. If compatibility requires additional historic tokens, enumerate them explicitly.
  - **Acceptance for patch pass:** For settings with both true and false defaults, test missing keys, canonical `true/false`, `on/off`, `1/0`, mixed case, leading/trailing whitespace if supported, blank values, and malformed values. Valid existing configurations must retain behavior; malformed values must fall back predictably to the caller-provided default and should optionally generate non-sensitive diagnostics rather than silently changing behavior.

- [ ] **O021 — Updater accepts spoofable post-handshake IPC that can mutate the replacement target and expected hash**
  - **Priority / state:** Medium / same-integrity local IPC and file-replacement boundary; SOURCE-CONFIRMED.
  - **Finding:** The updater's `WndProc` accepts update-data `WM_COPYDATA` whenever the message's caller-supplied `wParam` numerically equals the main application's stored message-window handle. Windows does not authenticate that convention: another same-integrity local process can send a message while placing that known handle value in `wParam`. More importantly, the updater leaves this receiver active for its full lifetime and stores the packet into mutable `UpdateData`. After the legitimate synchronous handshake has completed (and even after the main process exits), a forged packet can therefore replace `UpdateData.FileName` and `UpdateData.UpdateHash` before `RunUpdate` performs backup/move/launch. The filename is only checked for nonblank text and an `.exe` suffix; it is not constrained to the application directory or original target. With a public matching release hash, this permits a same-user/local sender that wins the race to redirect the legitimate downloaded executable onto another writable `.exe` path and have the updater launch it. This is not a remote attack or privilege-escalation claim; integrity boundaries such as UIPI still apply.
  - **Evidence:** `youtube-dl-gui-updater/Forms/frmUpdater.cs`, `WndProc`: accepts when `m.WParam == ApplicationData.MessageHandle`, assigns `UpdateData = CopyData.GetParam<UpdateData>(...)`, lowercases the hash, appends `.exe` if needed, and does not disable future packets. `RunUpdate` later derives `BackupLocation`, moves `UpdateDestination` to `UpdateData.FileName`, and starts that path. `Controls/CopyData.cs` exposes ordinary `SendMessage`; there is no session nonce or one-shot state in the packet. The main application intentionally provides release hash/version/filename during the legitimate request, but the updater does not freeze that accepted state afterward.
  - **Audit rationale checkpoint:** This is the updater-side counterpart to the pre-existing O007 requester-binding concern, but the concrete consequence is different: O007 concerns who may request/drive the main application's update handshake; O021 concerns mutation of the updater's file/hash target after that handshake. A narrow fix can make update-data acceptance one-shot, validate/freeze the target to the expected application path/name, and bind the exchange to a session the attacker cannot spoof merely by copying a HWND value.
  - **Acceptance for patch pass:** Use a real updater window plus a controlled sender process. Verify a valid main-app packet is accepted exactly once, then send packets with spoofed `wParam`, alternate writable absolute/relative paths, traversal-like names, different hashes/versions, and packets after the main process has exited. None may change the frozen update target or expected hash. Normal synchronous acknowledgement and update completion must still work, and invalid/spoofed messages must never cause the main process to close or any unrelated file to be moved/deleted/launched.

- [ ] **O022 — Settings tool-update handlers can resume after the Settings form is disposed**
  - **Priority / state:** Low-to-Medium / UI lifecycle and update-operation ownership; SOURCE-CONFIRMED.
  - **Finding:** The Settings redownload handlers are `async void` and do not tie their awaited work to the form lifetime. `btnSettingsRedownloadFfmpeg_Click` awaits `Updater.UpdateFfmpeg`; after the modal download dialog returns, that method performs archive extraction/replacement with `Task.Run` awaits, so the Settings UI becomes pumpable again while the operation is still pending. Save, Cancel, or window close can dispose Settings during that interval. The continuation then reads `this.Location`, plays result UI, shows a message, and writes `btnSettingsRedownloadFfmpeg.Enabled` without an `IsDisposed`/handle guard. The yt-dlp update-check handler likewise resumes after `CheckForYoutubeDlUpdate` and mutates controls/uses the form location without a lifetime guard. This can produce late UI work or disposed-control exceptions after the user has closed Settings, and the underlying tool update has no Settings-owned cancellation contract.
  - **Evidence:** `youtube-dl-gui/Forms/frmSettings.cs`: lines 682-714 implement the two `async void` handlers and touch form/control state after `await` with no disposal check. `Updater.UpdateFfmpeg` performs `await Task.Run(() => ...ExtractToFile...)` after its download dialog closes and before returning; `frmSettings_FormClosing` only restores settings and does not cancel or defer closure for these operations.
  - **Audit rationale checkpoint:** The update itself can remain owned by the application rather than by Settings if that is intended, but UI callbacks must not assume their initiating form still exists. A patch should explicitly choose whether closing Settings cancels the tool operation or merely detaches the initiating UI; either choice must prevent callbacks into disposed controls and avoid duplicate/reentrant update actions.
  - **Acceptance for patch pass:** Use delayed controlled metadata/download/extraction fixtures. Start each Settings redownload action, close/cancel/save Settings at every await boundary, and assert there is no unhandled exception, disposed-control access, orphaned modal dialog, or duplicate operation. If operations are intended to survive Settings closure, verify completion is reported through an application-owned surface and not the disposed form; if they are canceled, verify temp/backup cleanup and existing tool preservation. Also test closing the main application while detached work is active.
