# End-to-end review checklist — continuation 5

This file continues the prior end-to-end audit checklists. Findings are committed individually for interruption-safe recovery. Production source is unchanged in this review pass.

- [ ] **O032 — Downloader progress percentages are parsed but not bounded before assigning WinForms progress values**
  - **Priority / state:** Medium / live-output robustness; SOURCE-CONFIRMED residual coverage gap.
  - **Finding:** `DownloadHelper.GetTransferData` uses invariant `float.TryParse` and returns parsed progress through a `ref float`, but it does not constrain the value to the UI's valid range. Both `frmDownloader` and `frmExtendedDownloader` subsequently execute `pbStatus.Value = (int)Math.Floor(Percentage)` on their UI thread while the progress bar uses the normal 0–100 range. Thus a syntactically valid provider line such as `[download] 101% ...` (or a much larger numeric percentage) passes the parser but can produce `ArgumentOutOfRangeException` when assigned. In quick download that exception propagates back through `Control.Invoke` into the worker's broad catch, which marks the operation `ProgramError` and terminates the child; extended paths have the same unbounded assignment pattern. The existing `Progress.MalformedRowsCannotThrow` regression exercises `GetTransferData` in isolation and therefore does not cover this form-level sink.
  - **Evidence:** `youtube-dl-gui/Classes/DownloadHelper.cs`, `GetTransferData`, assigns `Percentage = ParsedPercentage` with no range check. `youtube-dl-gui/Forms/frmDownloader.cs` around the progress-processing loop assigns `(int)Math.Floor(Percentage)` to `pbStatus.Value`; `frmExtendedDownloader.cs` does the same in both single/batch processing loops. `ExtendedProgressBar` inherits WinForms ProgressBar range semantics.
  - **Audit rationale checkpoint:** Progress text from a child process is diagnostic/status input, not authority to break the transfer. Preserve the textual percentage if useful, but normalize/clamp or reject the numeric UI value before assigning it. Do not treat one malformed progress line as a downloader execution failure when the child can continue normally.
  - **Acceptance for patch pass:** Drive the actual quick and extended forms with a controlled provider emitting ordinary 0/0.1/99.9/100 percentages plus 101, huge finite values, negative, NaN/Infinity text, missing `%`, and culture-sensitive variants. The UI must never assign outside its valid range or change a successful child exit into ProgramError solely because of progress text. Valid ordinary progress display/ETA must remain unchanged; malformed lines should be logged/ignored or safely represented according to a documented policy.
