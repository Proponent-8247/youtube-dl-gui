  - **Evidence:** `youtube-dl-gui/Forms/frmMain.cs`, constructor: inside the non-Debug branch the subtitle menu item is both disabled and hidden before normal UI use. `frmSubtitles` remains incomplete, but that fact alone does not establish reachable Release behavior.
  - **Audit accountability:** The original O027 commit is retained because published history is forward-only. This correction supersedes its shipping classification. Do not implement a subtitle feature merely to “fix O027”; feature completion belongs to a separately authorized scope.

- [ ] **O028 — Cookies-from-Browser help link is exposed but has an empty click handler**
  - **Priority / state:** Low / authentication UX and feature discoverability; SOURCE-CONFIRMED.
  - **Finding:** The shipping authentication dialog includes a focusable `ExtendedLinkLabel` rendered as `?` next to the Cookies-from-Browser field. It is wired to `llCookiesFromBrowserHint_LinkClicked`, but that event handler is empty. Clicking the link therefore provides no explanation, validation, documentation, or feedback even though the field expects a provider/browser expression that is not self-explanatory. This is separate from the actual Cookies-from-Browser argument generation, which is functional; the defect is the advertised help surface doing nothing.
  - **Evidence:** `youtube-dl-gui/Forms/frmAuthentication.Designer.cs` creates `llCookiesFromBrowserHint`, sets `TabStop = true`, text `?`, and wires `LinkClicked` to `llCookiesFromBrowserHint_LinkClicked`. `youtube-dl-gui/Forms/frmAuthentication.cs` defines that handler as an empty method body. The control is added to the normal authentication form without a Debug-only guard.
  - **Audit rationale checkpoint:** Do not invent a browser-cookie syntax or force a browser. The patch pass should either provide concise in-app guidance consistent with the downloader versions this application supports, navigate to the appropriate maintained documentation with an explicit HTTPS target, or remove/disable the link if no help contract is intended. Keep authentication behavior unchanged.
  - **Acceptance for patch pass:** Open the normal authentication form and exercise keyboard and mouse activation of the `?` link. It must produce a defined, accessible result (help text or approved documentation) and must not shell-launch arbitrary user-controlled content. Verify the Cookies-from-Browser field still accepts supported values, Cancel/Download behavior is unchanged, and localization/accessibility text is provided if the help is shown in-app.

- [ ] **O029 — Updater language parser still truncates values containing URLs or literal `//`**
  - **Priority / state:** Low-to-Medium / localization correctness; SOURCE-CONFIRMED residual of D034.
  - **Finding:** The main application's external-language parser was corrected to treat `//` as an inline comment only when it is outside quotes and preceded by whitespace, preserving URLs and quoted literal slashes. The updater has a separate copy of the parser that still executes `Input = Input.Contains("//") ? Input.Substring(0, Input.IndexOf("//")) : Input` for every key/value line. Therefore an updater-localized string containing `https://...`, `http://...`, or a literal `//` is silently truncated even though the same syntax is preserved by the application's parser. The updater loads the application's selected external language file at startup, so this is a reachable parser divergence rather than dead code.
  - **Evidence:** `youtube-dl-gui/Language.cs`, `GetControlInfo`, contains the quote/whitespace-aware inline-comment scanner introduced by the D034 repair. `youtube-dl-gui-updater/Language.cs`, `GetControlInfo`, unconditionally truncates at the first `//`; `Program.cs` reads `LanguageFile` from the application's INI and calls `Language.LoadLanguage` against the shared `lang` directory.
  - **Audit rationale checkpoint:** The updater and application should interpret the same language-file value grammar consistently. This is not a request to remove inline comments. Reuse or mirror the already-defined main-parser semantics and preserve existing escape handling (`\\n`, `\\r`) and missing-key English fallback.
  - **Acceptance for patch pass:** Run the actual updater parser against values containing ordinary text, `https://example.invalid/help?a=1`, `http://...`, `value // comment`, quoted `"literal // content" // comment`, escaped quotes/backslashes, empty values, and multiple `=` characters. Assert updater results match the main application's intended parser behavior for the shared grammar and that malformed language files still fall back/report according to existing updater policy.

- [ ] **O030 — Converter preflight lets malformed batch-supplied paths escape the operation error boundary**
  - **Priority / state:** Low-to-Medium / conversion input robustness; SOURCE-CONFIRMED.
  - **Finding:** `frmConverter.BeginConversion` prevents input/output self-overwrite by calling `Path.GetFullPath` on `CurrentConversion.InputFile` and `OutputFile` before the conversion worker and its `try/catch` are created. The normal main-form converter fields are read-only and populated by dialogs, but the shipping Batch Converter uses editable `ExtendedTextBox` controls and queues their text verbatim into `ConvertInfo`. A user can therefore enter malformed Windows path text (for example characters/structures rejected by the Framework path parser); when the child converter is shown, `Path.GetFullPath` throws through the WinForms event path rather than setting `ConversionStatus.ProgramError` and returning a batch error result. Global thread-exception reporting may catch the UI exception, but the conversion item is not handled as an ordinary invalid-input failure and batch state can be left inconsistent.
  - **Evidence:** `youtube-dl-gui/Forms/frmBatchConverter.cs`, `AddItem`, copies editable input/output textbox text directly into its queues and later constructs `ConvertInfo(InputFile, OutputFile)`. `frmBatchConverter.Designer.cs` does not mark those `ExtendedTextBox` controls read-only. `youtube-dl-gui/Forms/frmConverter.cs`, `BeginConversion`, calls `Path.GetFullPath` for the equality check before the conversion-thread `try/catch` and without its own path-exception handling.
  - **Audit rationale checkpoint:** The self-overwrite guard is correct functionality and must remain. The defect is only where path normalization failure is handled. Validate/normalize once at the converter boundary and convert malformed/inaccessible syntax into the same contained ProgramError/batch result model as missing input/output rather than relying on the global exception UI.
  - **Acceptance for patch pass:** Queue normal absolute paths, same input/output, relative paths if supported, nonexistent-but-syntactically-valid input, invalid path characters/structure, very long paths at the supported runtime boundary, UNC paths, and valid Unicode paths through both Batch Converter and direct converter construction. Invalid syntax must produce a contained conversion error and deterministic batch item status with no application-level exception; same-file protection and normal dialog-generated paths must remain unchanged.

- [ ] **O031 — Merger drag/drop handlers trust `FileDrop` to contain a non-empty filename array**
  - **Priority / state:** Low / inter-application input robustness; SOURCE-CONFIRMED.
  - **Finding:** `frmMerger_DragEnter` checks only `GetDataPresent(DataFormats.FileDrop)`, casts the returned object to `string[]`, then immediately evaluates `Files[0]`. `frmMerger_DragDrop` performs the cast and forwards the array without checking the format, null result, or length. Normal Explorer drags provide a non-empty array, but drag/drop is an inter-process data boundary: another application/control can advertise `FileDrop` while supplying an empty/malformed payload, causing `IndexOutOfRangeException`, `InvalidCastException`, or `NullReferenceException` on the UI event path instead of simply rejecting the drag. The Debug-only Extended Converter has the same assumption, but the shipping Merger alone establishes reachability.
  - **Evidence:** `youtube-dl-gui/Forms/frmMerger.cs`, `frmMerger_DragEnter`: `string[] Files = (string[])e.Data.GetData(DataFormats.FileDrop); e.Effect = File.Exists(Files[0]) ...`. `frmMerger_DragDrop` likewise directly casts `GetData` and calls `AddFilesAsync(Files)`. No validation ensures `e.Data`/payload type/non-empty entries before indexing.
  - **Audit rationale checkpoint:** Do not restrict legitimate multi-file drag/drop or Explorer integration. Treat the drag data exactly like another input source: verify the format object is present, is a string array, contains at least one nonblank existing file (or let the existing per-file probe reject individual entries), and return `DragDropEffects.None` for malformed input without surfacing the global exception dialog.
  - **Acceptance for patch pass:** Drive the real form with normal one/multi-file Explorer-style payloads plus controlled `IDataObject` cases: missing FileDrop, null data, wrong type, empty array, blank entries, directory-only entries, mixed valid/invalid files, and disposal during async probing. Malformed drag data must be rejected without exception; valid files must retain current ordered probing/queue behavior and cancellation on form disposal.
