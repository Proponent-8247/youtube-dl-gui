- [ ] **O021 — An abandoned single-instance mutex can crash the next application launch**
  - **Priority / state:** Medium / startup availability and crash recovery; SOURCE-CONFIRMED.
  - **Finding:** The Release startup path constructs the named application mutex and immediately calls `WaitOne(TimeSpan.Zero, true)` without handling `AbandonedMutexException`. .NET signals an abandoned mutex by throwing that exception while granting ownership to the waiter. If a previous youtube-dl-gui process is killed or terminates abnormally while owning the mutex, the next launch can therefore escape `Main` through an unhandled exception instead of recognizing that the prior owner is gone and continuing startup. This affects recovery after a crash/forced termination rather than normal orderly shutdown.
  - **Evidence:** `youtube-dl-gui/Program.cs`, Release branch in `Main`: `if (!(Instance = new(true, ProgramGUID)).WaitOne(TimeSpan.Zero, true)) { ... return 1152; }` has no `AbandonedMutexException` handling around the named-mutex acquisition. Normal shutdown later calls `Instance?.ReleaseMutex()`.
  - **Audit rationale checkpoint:** An abandoned mutex means the single-instance lock is now available but its previous owner died; it is not evidence that another live instance should block startup. The correct recovery is to retain/accept ownership and continue while logging the abnormal prior termination. Do not remove the single-instance guard or create a second competing message window.
  - **Acceptance for patch pass:** Start a fixture instance that owns the exact named mutex and terminate it without release, then launch the application and assert startup proceeds without an unhandled exception and the new process owns the mutex. Also test normal first launch, normal second-instance forwarding, orderly release/relaunch, and repeated forced-termination recovery. Ensure ownership is released exactly once on the successful startup path.
