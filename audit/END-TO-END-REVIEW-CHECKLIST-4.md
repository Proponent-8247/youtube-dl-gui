# End-to-end review checklist — continuation 4

This file continues the prior end-to-end audit checklists. Each confirmed issue is committed individually so the review can recover cleanly after interruption. Production source is unchanged in this pass.

- [ ] **O027 — Shipping Subtitle Downloader UI has no download implementation**
  - **Priority / state:** Medium / exposed feature correctness; SOURCE-CONFIRMED.
  - **Finding:** The normal Release Tools menu exposes `mDownloadSubtitles`, which opens `frmSubtitles` modally. The form presents a URL field, uploaded/generated subtitle checkboxes, language selection controls, and a localized Download button. That button is wired to `btnSubtitlesDownload_Click`, but the handler body is completely empty. As a result, users can configure the advertised subtitle-download operation and click Download with no downloader invocation, validation, feedback, state change, or error. This is not a Debug-only/experimental route: the main menu item is added unconditionally in the shipping designer and its click handler opens the form in normal builds.
  - **Evidence:** `youtube-dl-gui/Forms/frmMain.Designer.cs` adds `mDownloadSubtitles` to `mTools`; `frmMain.mDownloadSubtitles_Click` creates and shows `frmSubtitles`; `youtube-dl-gui/Forms/frmSubtitles.Designer.cs` wires `btnSubtitlesDownload.Click` to `btnSubtitlesDownload_Click`; `youtube-dl-gui/Forms/frmSubtitles.cs` defines that handler with an empty body. The file comments already outline intended yt-dlp subtitle flags (`--write-sub`, `--write-auto-sub`, `--all-subs`, `--sub-lang`, `--sub-format`, `--skip-download`) but no operation uses them.
  - **Audit rationale checkpoint:** An exposed no-op control is a functional defect, but the patch pass must not invent subtitle semantics from comments alone. Preserve the visible feature intent and first determine the intended combinations of uploaded/generated/all subtitles, language text, output location/format, authentication/custom-provider behavior, and whether the existing downloader form should own execution/cancellation. If the feature is intentionally unfinished, hide/disable it in Release with an explicit status rather than presenting a working Download action that does nothing.
  - **Acceptance for patch pass:** Define expected behavior before implementation, then exercise at least uploaded-only, generated-only, both, all languages, explicit language list, invalid/empty URL, no selected subtitle source, provider error, cancellation, and output-path handling. Verify generated arguments use `ArgumentList`/operand separation, preserve supported URLs/search operands, do not leak credentials, and are executed through an owned/cancellable downloader path. If the decision is to disable the unfinished feature, assert Release no longer advertises an actionable subtitle downloader while Debug/development access remains intentional and documented.

- [ ] **O028 — Cookies-from-Browser help link is exposed but has an empty click handler**
  - **Priority / state:** Low / authentication UX and feature discoverability; SOURCE-CONFIRMED.
  - **Finding:** The shipping authentication dialog includes a focusable `ExtendedLinkLabel` rendered as `?` next to the Cookies-from-Browser field. It is wired to `llCookiesFromBrowserHint_LinkClicked`, but that event handler is empty. Clicking the link therefore provides no explanation, validation, documentation, or feedback even though the field expects a provider/browser expression that is not self-explanatory. This is separate from the actual Cookies-from-Browser argument generation, which is functional; the defect is the advertised help surface doing nothing.
  - **Evidence:** `youtube-dl-gui/Forms/frmAuthentication.Designer.cs` creates `llCookiesFromBrowserHint`, sets `TabStop = true`, text `?`, and wires `LinkClicked` to `llCookiesFromBrowserHint_LinkClicked`. `youtube-dl-gui/Forms/frmAuthentication.cs` defines that handler as an empty method body. The control is added to the normal authentication form without a Debug-only guard.
  - **Audit rationale checkpoint:** Do not invent a browser-cookie syntax or force a browser. The patch pass should either provide concise in-app guidance consistent with the downloader versions this application supports, navigate to the appropriate maintained documentation with an explicit HTTPS target, or remove/disable the link if no help contract is intended. Keep authentication behavior unchanged.
  - **Acceptance for patch pass:** Open the normal authentication form and exercise keyboard and mouse activation of the `?` link. It must produce a defined, accessible result (help text or approved documentation) and must not shell-launch arbitrary user-controlled content. Verify the Cookies-from-Browser field still accepts supported values, Cancel/Download behavior is unchanged, and localization/accessibility text is provided if the help is shown in-app.
