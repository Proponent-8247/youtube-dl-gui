# End-to-end review checklist — continuation

This checklist continues `audit/FINDINGS-CHECKLIST.md` for the full end-to-end pass begun September 9, 2026. Each issue is committed when confirmed so an interruption leaves a recoverable audit trail. Entries record concise audit rationale and evidence, not private chain-of-thought. Production code is not changed in this pass.

- [ ] **O009 — Updater hash mismatch can be overridden and executed**
  - **Priority / state:** High / local update integrity boundary; SOURCE-CONFIRMED.
  - **Finding:** `Updater.BeginUpdate` compares the updater file to the build-pinned `GeneratedUpdaterHash`, but a mismatch only blocks execution when the user answers **No** to a warning. Answering **Yes** continues to `Updater.Start()` with the mismatched executable. Because the expected hash is compiled into the application and the normal embedded resource is supposed to match it exactly, a mismatch is an integrity failure rather than an ordinary compatibility prompt. A local attacker or corrupted on-disk replacement able to alter `youtube-dl-gui-updater.exe` can therefore rely on user approval to cross the application's own integrity check. This does not by itself establish privilege escalation or a remote attack path.
  - **Evidence:** `youtube-dl-gui/Updater/Updater.cs`, `BeginUpdate`: after `CalculateSha256Hash(UpdaterPath) != KnownUpdaterHash`, execution is aborted only when `dlgUpdaterHashNoMatch` returns `DialogResult.No`; otherwise the code proceeds to construct and start the updater process.
  - **Audit rationale checkpoint:** The invariant is stronger than the prompt implies: the updater bytes are embedded in the same build and their SHA-256 is generated during packaging. There is no legitimate alternate updater hash accepted by this code path, so continuing on mismatch defeats the exact check. Preserve the existing user-facing error flow, but fail closed rather than offering an execution override.
  - **Acceptance for patch pass:** Replace the on-disk updater with controlled mismatched bytes and invoke the update path. Assert that no process starts regardless of dialog response, the invalid file is removed or safely replaced from the verified embedded resource, the freshly written resource is re-hashed before execution, and a matching updater still launches. Add a regression that would fail on the current Yes-to-continue behavior.

- [ ] **O010 — Downloaded application hash mismatch can be ignored and installed**
  - **Priority / state:** High / application-update integrity boundary; SOURCE-CONFIRMED.
  - **Finding:** `youtube-dl-gui-updater` calculates the downloaded application's SHA-256 and compares it to `UpdateData.UpdateHash`, but the mismatch dialog offers Abort/Retry/**Ignore**. Selecting Ignore returns successfully from `VerifyHash`; `RunUpdate` then moves the mismatched `update.part` over the application and launches it. This turns the release-integrity check into an advisory prompt. A corrupted or substituted update payload that reaches the updater can therefore be executed if the user chooses Ignore. This finding does not assume compromise of GitHub or TLS; it is about the local fail-open behavior after an explicit hash mismatch.
  - **Evidence:** `youtube-dl-gui-updater/Forms/frmUpdater.cs`, `VerifyHash`: `DialogResult.Ignore` sets progress state to normal and `return`s. `RunUpdate` immediately continues to move the file into `UpdateData.FileName` and `Process.Start(UpdateData.FileName)`.
  - **Audit rationale checkpoint:** A cryptographic expected hash is useful only if mismatch is terminal for that payload. Retry is a legitimate recovery path; Ignore is not equivalent because it deliberately accepts bytes the release metadata says are wrong. This is distinct from O009, which concerns integrity of the updater stub itself.
  - **Acceptance for patch pass:** Serve controlled bytes whose hash differs from the expected release hash. Assert the payload is never moved over the installed application and never launched. Retry may fetch a new payload, but no UI response may authorize mismatched bytes. Preserve rollback of the old application. Add tests for mismatch-abort, mismatch-retry-then-match, mismatch-retry-then-mismatch, and matching first download.

- [ ] **O011 — Closing the updater does not cancel metadata/download/replacement work**
  - **Priority / state:** Medium / updater lifecycle and user-intent boundary; SOURCE-CONFIRMED.
  - **Finding:** `Program.CancelToken` is created once in the updater and passed into GitHub metadata and file-download calls, but no production code ever calls `CancelToken.Cancel()` or disposes it. `frmUpdater` has no FormClosing/Disposed cancellation hook. `frmUpdater_Shown` starts `RunUpdate` as an `async void` handler, so closing/disposing the form does not cancel the in-flight operation; after awaited network work completes, the routine can continue verifying, replacing and launching the application even though the updater UI was closed.
  - **Evidence:** `youtube-dl-gui-updater/Program.cs` initializes `CancelToken = new()`; repository-wide updater search shows only token reads in `Classes/Github.cs` and `Forms/frmUpdater.cs`, no cancellation call. `frmUpdater_Shown` awaits `RunUpdate()` and no closing handler cancels it.
  - **Audit rationale checkpoint:** The token's presence shows cancellation was intended, but lifecycle ownership is incomplete. User-initiated close should not silently become “continue update headlessly.” This is related to O005 in the original checklist (uncancellable parent-process wait) but extends beyond that wait to metadata/download/replacement work.
  - **Acceptance for patch pass:** Start delayed metadata and delayed binary downloads, close the updater, and assert cancellation reaches both operations, temporary files are cleaned without replacing the installed application, no new application process launches, and no callback touches disposed controls. Separately test close while waiting for the parent process. Dispose the token at process shutdown.

- [ ] **O012 — “View in browser” can shell-launch an arbitrary queued source**
  - **Priority / state:** Medium / local shell-launch trust boundary; SOURCE-CONFIRMED.
  - **Finding:** The extended downloader's link label and queue context-menu actions pass `MediaDetails.URL` directly to `Process.Start(string)`. Queue construction accepts any nonblank string and does not require an `http`/`https` URI; clipboard scanning can also enqueue arbitrary clipboard text when link verification is disabled. On the targeted .NET Framework/Windows behavior, `Process.Start(string)` uses shell association for such inputs, so an executable path, document association, or custom URI scheme can be invoked when the user chooses an action labeled “view in browser.” This is an explicit-click path, not drive-by execution, and no privilege escalation claim is made.
  - **Evidence:** `youtube-dl-gui/Forms/frmExtendedDownloader.cs`: `QueueNewItem` rejects only null/empty/whitespace sources; `llbLink_LinkClicked` and `mQueueViewInBrowser_Click` each call `Process.Start(MediaDetails.URL)` without URI/scheme validation. `MediaData` trims a small set of control/quote characters but does not constrain the source scheme or file type.
  - **Audit rationale checkpoint:** Downloader inputs intentionally support more than web URLs (search expressions, paths, provider-specific sources), so validation must be applied to the **browser-launch action**, not globally to download inputs. The UI label creates a narrower promise than the data model. A safe change must preserve accepted downloader operands while refusing or explicitly handling non-web navigation targets.
  - **Acceptance for patch pass:** Exercise `https`, `http`, `file:`, a local `.exe` path, a document path, an unknown/custom protocol, a search expression, UNC input and malformed URI text. Browser action must launch only approved web schemes (or present a clear non-executing error); download behavior for non-web operands must remain unchanged. Add regression coverage around the launch-target validator rather than actually executing arbitrary local files.

- [ ] **O013 — Second-instance IPC can hang indefinitely on a blocked first-instance UI thread**
  - **Priority / state:** Medium / availability and single-instance correctness; SOURCE-CONFIRMED.
  - **Finding:** In Release builds, a second application instance locates the first instance's hidden message window and forwards download/show requests with synchronous Win32 `SendMessage`. The wrapper has no timeout. `SendMessage` does not return until the target window procedure processes the message, so a hung or blocked first-instance UI thread can hang the new process indefinitely. The updater handshake has the same primitive, but its wait/handshake risks are already tracked separately in O005/O011.
  - **Evidence:** `youtube-dl-gui/Program.cs` sends both `WM_COPYDATA` and `WM_SHOWFORM` using `CopyData.SendMessage`; `Controls/CopyData.cs` imports `user32!SendMessage` and has no `SendMessageTimeout` path. The target `MessageHandler.WndProc` runs on the first instance's UI thread.
  - **Audit rationale checkpoint:** Single-instance forwarding should be best-effort IPC, not an unbounded dependency on another UI thread. The intended behavior can be preserved with a finite timeout and a defined fallback/error exit; no need to remove the mutex or message protocol.
  - **Acceptance for patch pass:** Create a first-instance fixture whose message window deliberately stops pumping messages, launch a second instance with both a show request and a download request, and assert it exits or reports failure within a finite deadline. Verify normal forwarding still succeeds and payload memory is freed on timeout/failure. Use a timeout-capable Windows message API without introducing duplicate downloads.

- [ ] **O014 — Extended downloader misrecognizes Windows-relative download roots**
  - **Priority / state:** Medium / output-path correctness; SOURCE-CONFIRMED residual of historical F039.
  - **Finding:** Settings and the quick downloader treat both `./relative` and `.\\relative` as paths relative to the application directory. `ExtendedMediaDetails.GenerateArguments`, however, tests `Downloads.downloadPath.StartsWith("\\.")` instead of `StartsWith(".\\")`. A configured `.\\downloads` root therefore follows different path construction in extended mode than in quick mode. This is a current-source residual despite the earlier relative-root repair history.
  - **Evidence:** `youtube-dl-gui/Classes/DataClasses/ExtendedMediaDetails.cs` uses `StartsWith("./") || StartsWith("\\.")` before slicing `[2..]`; `Classes/DataClasses/DownloadInfo.cs` and `Forms/frmSettings.cs` use the intended `StartsWith("./") || StartsWith(".\\")` form.
  - **Audit rationale checkpoint:** The behavior is already defined consistently by Settings and the quick downloader, so this is not a policy question. Extended mode should use the same normalized root. The correction should be narrowly scoped rather than refactoring all path construction during a bug fix.
  - **Acceptance for patch pass:** Generate quick and extended arguments for an absolute root, `./relative`, `.\\relative`, a UNC root and a drive-root path. Assert both download modes resolve each root consistently, preserve UNC semantics, and do not truncate the first two characters of absolute inputs. Add a direct regression for `.\\relative` in extended mode.
