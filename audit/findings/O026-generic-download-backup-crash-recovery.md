- [ ] **O026 — Generic download replacement does not recover an orphaned backup before a new attempt**
  - **Priority / state:** Medium / file replacement durability and crash recovery; SOURCE-CONFIRMED residual of the historical replacement work.
  - **Finding:** `frmGenericDownloadProgress.RunDownload` transactionally handles exceptions thrown while moving a newly downloaded temp file into place, but it has no startup recovery for a prior interrupted replacement. The normal sequence is: download `Output.tmp`; delete stale backup only when both backup and live output exist; move live `Output` to `Output.bck`; then move temp to live output. If the process/OS terminates after the live file is moved to `.bck` and before the temp move completes, the next run sees `Output` missing and `BackupFile` present but immediately deletes/re-downloads the temp. If that new download fails or is cancelled, the known-good file remains stranded as `.bck` and the expected live path stays missing. This is especially impactful when the generic form is used to replace executable dependencies.
  - **Evidence:** `youtube-dl-gui/Forms/frmGenericDownloadProgress.cs`, `RunDownload`: startup only deletes `TempFile`; backup cleanup/creation occurs after network completion, and restoration of `BackupFile` exists only inside the inner catch around `File.Move(TempFile, Output)`. There is no `if (!File.Exists(Output) && File.Exists(BackupFile)) restore` recovery before starting a new attempt.
  - **Audit rationale checkpoint:** Exception rollback and crash recovery are different guarantees. The existing `.bck` convention already expresses which file is the last known-good output, so an interrupted previous transaction should be reconciled before any new network dependency. The correction should preserve retry semantics and must not overwrite a newer valid `Output` with a stale backup when both exist.
  - **Acceptance for patch pass:** Fault-inject termination at each replacement boundary: before backup move, after `Output -> .bck`, after `.tmp -> Output`, and during cleanup. On restart, assert exactly one usable live output is recovered before network work; a subsequent offline/cancelled attempt must not strand the valid prior file. Cover cases with only Output, only Backup, only Temp, Output+Backup, Backup+Temp, and all three, with sentinel contents so stale/new files cannot be confused. Verify provider/app/tool update callers retain their intended behavior.
