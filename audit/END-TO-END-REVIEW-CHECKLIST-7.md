# End-to-end review checklist — continuation 7

This file continues the prior end-to-end audit checklists. Findings are committed individually for interruption-safe recovery. Production source is unchanged in this review pass.

- [ ] **O040 — `BetterFolderBrowser` does not dispose the native dialog objects it owns**
  - **Priority / state:** Low / native resource ownership; SOURCE-CONFIRMED and shipping-reachable.
  - **Finding:** Application call sites correctly wrap `BetterFolderBrowser` in `using`, but disposing that outer component does not dispose the actual dialog object it owns. `BetterFolderBrowser` holds a readonly `BetterFolderBrowserDialog`; that helper holds a readonly `OpenFileDialog ofd`, yet neither helper implements/disposes it and the outer `Dispose(bool)` only disposes its `components` container. On non-Vista/Wine fallback, `ShowDialog` also creates a `FolderBrowserDialog` without `using`/Dispose. Both dialog types are disposable WinForms components that can allocate native resources after display. Repeated Browse/first-run folder selection can therefore delay release of dialog/native resources until finalization/GC despite callers believing the `using BetterFolderBrowser` scope owns them deterministically.
  - **Evidence:** `Controls/BetterFolderBrowser.cs`: outer `BetterFolderBrowser.Dispose(bool)` disposes only `components`; `_dialog` has no disposal call. `BetterFolderBrowserDialog` constructs `private readonly OpenFileDialog ofd` and does not implement `IDisposable`. Its fallback branch constructs `FolderBrowserDialog fbd = new()` without disposal. Shipping usages in `Program.FirstTimeSetup`, `frmMain` and `frmSettings` all use the outer wrapper in a `using`, so they demonstrate intended deterministic ownership that the implementation currently fails to propagate.
  - **Audit rationale checkpoint:** Preserve the current folder-selection UI and reflection-based Vista picker. The fix should make the wrapper's ownership explicit—dispose the inner `OpenFileDialog` when the outer wrapper is disposed and scope the fallback `FolderBrowserDialog`—without disposing shared framework objects or breaking repeated ShowDialog calls before outer disposal.
  - **Acceptance for patch pass:** Repeatedly create/show/cancel/dispose the wrapper using both the Vista-style path and a controllable fallback path where testable. Verify native/User/GDI handle counts do not grow monotonically, no ObjectDisposedException occurs during a normal single wrapper lifetime, selected path/multiselect/title/root behavior stays unchanged, and existing `using BetterFolderBrowser` call sites need no behavioral rewrite. Include a focused lifecycle/resource regression or handle-count stress with a conservative tolerance for framework caching.

- [ ] **O041 — Remote language `name` is appended as a Windows path without constraining it to the `lang` directory**
  - **Priority / state:** Medium / remote-content file-write boundary; SOURCE-CONFIRMED cross-platform path canonicalization risk.
  - **Finding:** Available language entries come from GitHub's repository-contents API and the UI filters only for nonblank `name` and `download_url`. When the user downloads one, `frmDownloadLanguage` constructs `Output = Environment.CurrentDirectory + "\\lang\\" + lang.name` and passes it to the generic replacement downloader without validating the final full path, basename, extension, or Windows directory separators. Git/GitHub path components are POSIX-oriented: a backslash is not the repository path separator and can be part of a filename, while on Windows the same backslash becomes a path separator. A trusted-upstream compromise/malicious repository entry named like `..\\target` can therefore be interpreted by this Windows client as traversal out of `lang` and make the download/replacement machinery write to another writable path relative to the application directory. This finding does not claim GitHub itself injects such names or that the current upstream language directory contains one; it identifies the missing client-side confinement at a remote-metadata-to-filesystem boundary.
  - **Evidence:** `youtube-dl-gui/Updater/Updater.cs`, `GetAvailableLanguages`, returns repository content entries other than `English.ini` without enforcing `type`, `.ini` basename, or path rules. `youtube-dl-gui/Forms/frmDownloadLanguage.cs` filters only `name`/`download_url`, displays the remote name, and later concatenates `lang.name` directly to the Windows `lang\\` destination passed to `frmGenericDownloadProgress`. The generic downloader treats its supplied output as an authoritative filesystem destination and performs temp/backup replacement there.
  - **Audit rationale checkpoint:** Language selection is remote content, not authority to choose arbitrary client filesystem targets. Constrain the accepted entry to a simple Windows-safe filename (and likely the intended `.ini` type), combine it with the fixed language directory, canonicalize both, and assert the result remains a direct child of that directory. This complements P003/V008 publisher-authenticity review; publisher trust does not remove the need for path confinement on externally supplied metadata.
  - **Acceptance for patch pass:** Feed controlled repository-content metadata containing normal `Spanish.ini`, nested/path-like forward slashes, backslashes, `..\\outside.ini`, dot/dot-dot names, rooted/drive/UNC-like strings, reserved Windows names, trailing dot/space, unexpected extensions/types, Unicode filenames, and a valid download URL. Only intended simple language files may be offered/downloaded; the canonical destination must remain inside the language directory and existing unrelated files must never be touched. Verify normal language downloads, overwrite/retry behavior, and selected-language refresh still work. Add a regression at the actual `GithubRepoContent` → form → generic-download destination boundary rather than testing a path helper alone.

- [ ] **O042 — Fixed documentation/support URL launches do not contain shell-association failures**
  - **Priority / state:** Low / UI help-link fault containment; SOURCE-CONFIRMED.
  - **Finding:** Multiple normal help/support actions call `Process.Start("https://...")` directly from WinForms events or update fallback paths with no local exception handling. If the machine has no usable HTTPS shell association, application-control policy blocks the launch, or shell execution otherwise fails, clicking a documentation/support link can surface the global exception UI instead of a contained “could not open browser” result. Affected paths include About/repository links, supported-sites documentation, Settings output-template/protocol help, exception-report issue links, and the updater-disabled TLS fallback that opens the Releases page. This is distinct from O012, where the URL is externally sourced and therefore also a security/trust concern; O042 concerns fixed developer-selected HTTPS links only.
  - **Evidence:** Direct unguarded fixed-URL `Process.Start` calls occur in `frmAbout.cs`, `frmMain.cs` supported-sites actions, `frmSettings.cs` documentation/protocol links, both application/updater exception forms, and `Updater.CheckForUpdate` when TLS 1.2+ is unavailable. None uses a shared safe-launch wrapper or catches `Win32Exception`/related start failures locally.
  - **Audit rationale checkpoint:** Keep the intended browser navigation and fixed HTTPS destinations. Centralize or consistently contain shell launch failures, report them locally/non-recursively, and do not route fixed links through a permissive arbitrary-URI launcher that would weaken O012's boundary.
  - **Acceptance for patch pass:** Exercise each fixed-link category with a normal HTTPS handler, no/default-browser association, a controlled shell-launch failure/policy denial, and disposed/closing owner forms where applicable. Failure must not generate an unhandled/global exception or recursively fail through the exception-report UI; normal links must still open exactly the intended fixed HTTPS target. Keep arbitrary media URLs governed by O012 rather than treating them as trusted help links.
